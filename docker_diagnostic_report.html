Kimodo Docker 配置诊断报告

日期: 2026-05-28  |  环境: RTX 5090 x8, NVIDIA Driver 575.64.03, CUDA 12.9

问题总结

现象：docker compose up 启动 text-encoder 容器时，健康检查失败，demo 容器无法启动。

根因：Docker entrypoint 脚本根据 /workspace 目录的 UID/GID 切换到非 root 用户运行。宿主机目录挂载到 /workspace 后，UID 变为普通用户，该用户无权访问 /dev/nvidia* GPU 设备，导致 PyTorch 的 CUDA 初始化失败。

修复：在 docker-compose.yaml 中设置 HOST_UID=0、HOST_GID=0，强制以 root 运行。

三、问题 #1：健康检查超时

现象

dependency failed to start: container text-encoder is unhealthy

text-encoder 容器启动后，健康检查在模型加载完成前就判定失败。

根因

原始健康检查配置：interval: 3s, retries: 40，总计等待 120 秒。LLM2Vec-Llama-3-8B 模型加载需要 3-5 分钟，远超此限制。

修复

healthcheck:
  interval: 10s
  timeout: 5s
  retries: 60
  start_period: 300s    # 新增：5 分钟宽限期

四、问题 #2：容器无法访问外网

现象

text-encoder 容器状态: health: starting（持续数分钟）
容器内 curl https://huggingface.co → 超时
容器内存: 508 MiB（模型未加载到 GPU）

进程在运行（CPU 17%），但模型没有加载到 GPU，无任何日志输出。

根因

Docker 容器网络无法访问 huggingface.co。LLM2Vec.from_pretrained() 即使模型已缓存本地，仍会尝试联网检查更新，导致进程卡死在网络请求上。

修复

在 docker-compose.yaml 的 environment 中添加：

- HF_HUB_OFFLINE=1
- TRANSFORMERS_OFFLINE=1

强制离线模式，使用本地缓存。

五、问题 #3：容器退出码 137

现象

text-encoder exited with code 137

根因

退出码 137 = 128 + 9 (SIGKILL)。在问题 #2 修复前，模型加载卡死导致容器被系统回收。修复离线模式后此问题消失。

六、问题 #4：CUDA 不可用（核心问题）

现象

RuntimeError: No CUDA GPUs are available
UserWarning: Can't initialize NVML

即使模型成功加载到 CPU（17 GiB 内存），移动到 GPU 时 CUDA 初始化失败。

排查过程

Step 1：怀疑 NVIDIA_VISIBLE_DEVICES 配置
NVIDIA_VISIBLE_DEVICES=1 → CUDA: False
NVIDIA_VISIBLE_DEVICES=all → CUDA: True
结论：指定单卡索引会导致 NVML 初始化失败（5090 驱动兼容性问题）。
Step 2：怀疑 CUDA_VISIBLE_DEVICES
NVIDIA_VISIBLE_DEVICES=all + CUDA_VISIBLE_DEVICES=1 → CUDA: True（小张量测试）
结论：CUDA_VISIBLE_DEVICES 本身没问题。
Step 3：怀疑 HuggingFace 环境变量
+HF_HUB_OFFLINE=1 +TRANSFORMERS_OFFLINE=1 → CUDA: True
结论：环境变量不影响 CUDA。
Step 4：定位到 volume 挂载
docker run --rm --runtime=nvidia kimodo:1.0 python -c "..." → CUDA: True
docker run --rm --runtime=nvidia -v $HOME/kimodo:/workspace ... → CUDA: False
docker run --rm --runtime=nvidia -v $HOME/kimodo:/workspace2 ... → CUDA: True
挂载任意目录到 /workspace 导致 CUDA 失败！
Step 5：定位到 entrypoint 脚本
--entrypoint python（跳过 entrypoint）→ CUDA: True
问题出在 /usr/local/bin/docker-entrypoint 脚本。
Step 6：确认根因 — UID/GID 权限问题
entrypoint 脚本逻辑：
HOST_UID="$(stat -c %u /workspace)"  # 读取挂载目录的 UID
HOST_GID="$(stat -c %g /workspace)"
useradd -m -u "$HOST_UID" -g "$HOST_GID" "$HOST_USER"
exec gosu "$HOST_UID:$HOST_GID" "$@"   # 切换到该用户运行

宿主机目录 UID=1021（普通用户），容器内创建的用户无权访问 /dev/nvidia* 设备。

验证：
-e HOST_UID=0 -e HOST_GID=0 → CUDA: True

最终修复

在 docker-compose.yaml 的两个 service 中均添加：

# 以 root 运行，确保 GPU 设备访问权限
- HOST_UID=0
- HOST_GID=0
- HOST_USER=root

七、最终 docker-compose.yaml 关键配置

environment:
  - HF_HOME=/workspace/.cache/huggingface
  - HF_HUB_OFFLINE=1              # 离线模式
  - TRANSFORMERS_OFFLINE=1        # 离线模式
  - TEXT_ENCODER_DEVICE=cuda       # 强制 CUDA
  - HOST_UID=0                     # root 用户
  - HOST_GID=0
  - HOST_USER=root
  - NVIDIA_VISIBLE_DEVICES=all     # 可见所有 GPU
  - CUDA_VISIBLE_DEVICES=1         # 使用 GPU 1
  - NVIDIA_DRIVER_CAPABILITIES=compute,utility

healthcheck:
  interval: 10s
  timeout: 5s
  retries: 60
  start_period: 300s               # 5 分钟宽限期

八、经验总结

  1. entrypoint 用户切换需谨慎：当使用 volume 挂载宿主机目录时，目录的 UID/GID 会被传递到容器内。如果 entrypoint 依赖此信息切换用户，需要确保该用户有 GPU 设备访问权限。
  2. 离线模式：容器内无法访问外网时，必须设置 HF_HUB_OFFLINE=1，否则 HuggingFace 模型加载会卡死。
  3. 健康检查宽限期：大模型加载需要较长时间，健康检查应设置足够的 start_period。
  4. NVIDIA_VISIBLE_DEVICES 指定单卡索引：在某些 5090 驱动版本下会导致 NVML 初始化失败，建议用 NVIDIA_VISIBLE_DEVICES=all + CUDA_VISIBLE_DEVICES 替代。
